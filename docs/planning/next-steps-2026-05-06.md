# Next Steps — 2026-05-06

> Planning document. Not a spec, not an implementation guide. A ranked list of
> what to do next, with the reasoning behind each item so the implementer
> (Sonnet 4.6) can make sensible judgment calls when details surface.

---

## Where we are

**Built and working:**
- Postgres schema (suppliers, products, inventory, restaurants, orders, order_items, webhooks, bot_sessions)
- Supabase REST API (auto-generated by PostgREST)
- RLS posture: read-only-for-anon, writes via `service_role`
- Hand-written OpenAPI 3.1 spec at `api-spec/openapi.yaml` (319 lines)
- Supplier dashboard scaffold (Next.js + typed DB client + loading skeletons)
- WhatsApp bot end-to-end: signed receive → Zod parse → bot_sessions state machine → Graph API reply. Flow: list products → select → quantity → confirm → order placed.

**Known friction (not yet recorded in CLAUDE.md):**
- Cloudflare quick tunnel URL is ephemeral. Every bot restart requires re-registering the webhook with Meta. This is the single biggest blocker to bot iteration.
- Bot E2E flow works but has not been hardened (timeouts, retries, error UX, multi-product carts).

**Gaps relative to MVP scope in CLAUDE.md:**
- OpenAPI spec exists as a file but is not *served* anywhere. No `/docs` UI, no public URL. From an agent's POV, the contract is invisible.
- Idempotency keys are a column in the `orders` table but no endpoint actually enforces idempotency *semantics* (returning the cached response on duplicate keys). PostgREST will throw a unique-constraint error on the second request, which is not the contract our spec promises.
- Webhook delivery to suppliers on order events is in MVP scope but not implemented. The `webhooks` table exists; the dispatcher does not.
- No scoped API keys for third-party agents. Today: `anon` reads, `service_role` writes. No middle ground.
- RFC 7807 error envelope is promised by the spec but PostgREST returns its own error shape.

## Guiding principle for prioritization

**The API is the product. The bot is a wedge demo.** When two tasks compete, prefer the one that makes the API a more credible standalone product over the one that polishes the demo. The bot's value is proving the API works end-to-end with a real client, not being a great chatbot.

Corollary: anywhere PostgREST's auto-generated behavior diverges from the contract our OpenAPI spec promises, that divergence is a **product bug**, not a documentation bug. The spec is the contract.

## Recommended next steps, ranked

### 1. Stabilize the bot's webhook endpoint — deploy it somewhere with a stable URL
**Why first:** every other bot improvement is gated by the cost of restarting. Re-registering the Meta webhook on each restart is a ~5-minute manual loop that compounds. This is also a one-shot fix; once done, it stays done.

**Options to consider:**
- **Vercel** — easiest if the bot is already Node/TS. Cold starts are fine for webhook receivers. Bot state is in `bot_sessions` (DB), so stateless serverless works.
- **Fly.io / Railway** — long-running process, no cold starts, slightly more setup. Pick this if you anticipate background jobs (webhook retries, etc.) that benefit from a persistent worker.
- **Cloudflare named tunnel** — keeps the existing dev setup, just makes the URL stable. Cheapest change but least production-like.

**Recommendation:** Vercel for now. The bot is a single HTTP handler today; serverless is the natural shape. Revisit if/when we add a background worker for webhook retries (item 4).

**Trade-off to flag:** if Vercel, the webhook-dispatcher in item 4 cannot live in the same process as a long-running queue consumer. That pushes the dispatcher onto Supabase Edge Functions or `pg_cron`, which is fine but worth knowing up front.

**Done when:** Meta webhook is registered against a stable URL. Bot restarts (deploys) do not require re-registration.

---

### 2. Serve the OpenAPI spec at a public `/docs` URL
**Why:** "agent-native" without a published, browsable contract is just marketing. Today an agent author has to clone the repo to find `api-spec/openapi.yaml`. That breaks the entire pitch.

**Two parts:**
- **Serve the YAML** at e.g. `https://dashboard-host/openapi.yaml` (static asset on the dashboard).
- **Render it** at `/docs` using Stoplight Elements or Scalar (both are single-script embeds, no build step).

**Trade-off:** PostgREST also auto-generates an OpenAPI document from the schema. That document is technically more accurate (always in sync with the DB) but exposes PostgREST's quirky filter syntax (`?col=eq.value`, embed syntax, etc.) which is *not* the contract we want agents to learn. The hand-curated spec describes the API we *want to be*, even if some endpoints are still served by raw PostgREST today. Keep the hand-curated spec as the source of truth; the gap between it and reality is the to-do list.

**Done when:** anyone can visit `/docs`, see the API, and copy a `curl` example that works.

---

### 3. Build the `POST /v1/orders` Edge Function — make idempotency real
**Why:** this is the first endpoint where the spec and PostgREST diverge meaningfully. The spec promises "send the same `Idempotency-Key` twice, get the same order back." PostgREST will throw a 409 on the second call. That's a contract violation on the most important endpoint we have.

**Shape:**
- Supabase Edge Function at `/v1/orders` (POST).
- Validates body with Zod (matching the spec).
- Checks `idempotency_keys` table (new) — if key seen, return the stored response.
- Otherwise: insert order + items in a transaction, store the response keyed by idempotency_key, return 201.
- Wraps any error in RFC 7807 envelope.
- Emits an `order.created` event for the webhook dispatcher (item 4) to pick up.

**Trade-off:** every endpoint we wrap in an Edge Function is code we maintain instead of getting for free from PostgREST. That's a real cost. Counter-argument: the endpoints that need wrapping are exactly the ones where "the schema = the contract" breaks down (writes with side effects, idempotency, webhooks, auth scoping). Reads can stay on PostgREST.

**Done when:** posting the same idempotency key twice returns the same order_id with 200/201, not a 409. RFC 7807 error shape on validation failures.

---

### 4. Webhook delivery to suppliers on `order.created`
**Why:** this is in MVP scope and it's the supplier-side feedback loop. Without it, the supplier dashboard has to poll, and the API's "agent-native" story has no story for *push*. With it, the supplier dashboard becomes the first real consumer of our own webhook contract, which surfaces design bugs early.

**Shape:**
- `webhook_deliveries` table — id, webhook_id, event_type, payload, status (pending/sent/failed), attempts, next_attempt_at, response_code, response_body.
- Trigger or Edge Function call from item 3 enqueues a row.
- A worker (Edge Function on a schedule, or `pg_cron`-driven) picks up pending rows, POSTs to the supplier's URL with `X-Negatic-Signature` HMAC, retries with exponential backoff, gives up after N attempts.
- Supplier dashboard gets a "webhook events" page and a test-fire button (good DX, also useful for debugging).

**Trade-off — inline vs queued delivery:**
- *Inline* (POST inside the order-creation request): simple, but a slow/down supplier blocks order creation, and one failed delivery is lost. Bad.
- *Queued* (enqueue row, worker dispatches): correct, but requires a worker. Use this.

**Done when:** creating an order causes the supplier's registered webhook URL to receive a signed POST within ~5s, with retry on 5xx.

---

### 5. Scoped API keys for third-party agents
**Why:** unblocks the *second* AI agent integrating with Negatic — anyone who isn't us. Without this, the only auth modes are "anon read" and "service_role do anything." There's no safe credential to hand to a partner.

**Why not higher:** there is no second agent yet. Building this before there's a real consumer means designing in the dark. Items 1–4 close concrete gaps; this one closes a hypothetical gap.

**Shape (sketch — defer details until item 4 is done):**
- `api_keys` table — id, supplier_id, key_hash, scopes (jsonb), created_at, revoked_at.
- Edge Function middleware validates `Authorization: Bearer ...`, looks up scope, sets a `current_supplier_id` on the request.
- RLS policies on supplier-scoped tables key off this (or the function does the scoping in code, since Edge Functions use service_role).

**Done when:** a key can be issued for a supplier, used to read their own orders, and rejected when trying to read another supplier's.

## Explicitly not next (push back if asked)

These all sit *outside* the MVP scope in `CLAUDE.md`. Listed here so the implementer doesn't get nerd-sniped:

- **Multi-product cart in the bot.** One product per order is fine for MVP. Cart logic is bot polish, not API value.
- **Bot NLU / free-text parsing.** Button-based intent matching is explicitly the chosen design.
- **Restaurant-facing mobile app.** Out of scope.
- **Multi-supplier price comparison.** Out of scope until there's a second supplier.
- **Payments / billing.** Out of scope.
- **Email notifications.** Out of scope.
- **Analytics dashboards.** Out of scope.
- **Hardening the bot (rich error UX, retries, "did you mean", undo).** Worth doing eventually, but each hour spent here is an hour not spent making the API a real product. Defer until items 1–4 are done.

## Open questions worth resolving before starting

1. **Where does the bot deploy?** Vercel (recommended) or Fly/Railway? This affects whether the webhook dispatcher (item 4) co-locates with the bot or lives on Supabase Edge Functions.
2. **Is the dashboard ready to consume webhooks**, or is it still display-only? If display-only, item 4 should include a minimal "incoming events" view in the dashboard so the loop is observable.
3. **WhatsApp number status** — still using the Meta test number, or have we provisioned a real WABA number? Affects whether item 1's deploy can be considered "production-ready" or just "stable-dev."
4. **One unified `/v1/` host or split?** Today the spec says `https://api.negatic.dev/v1`. PostgREST is at `/rest/v1/`. Do we (a) put a reverse proxy in front and rewrite paths, (b) accept that the public URL is the PostgREST URL, or (c) only expose Edge Functions under `/v1/` and treat raw PostgREST as internal? This decision shapes items 2 and 3.

## Suggested sequencing

```
Week 1: item 1 (deploy bot) + item 2 (serve /docs)            ← unblocks everything else
Week 2: item 3 (orders Edge Function with idempotency)        ← first "real" API endpoint
Week 3: item 4 (webhook delivery)                             ← closes the supplier feedback loop
Later:  item 5 (API keys) when a second agent appears
```

Items 1 and 2 are independent and can run in parallel. Item 3 should land before item 4 (item 4 depends on the order-created event emission). Item 5 is the only one that's safe to defer indefinitely.
